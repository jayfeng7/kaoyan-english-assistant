# 第一课：先看懂检索，再接真实模型

本目录是独立教学实验，不是产品RAG模块。所有卡片为本项目原创演示说明，未经教师签核；二维向量手工指定，不是模型推理结果。没有付费调用、网络请求或学生材料。

在项目根目录运行：

```powershell
node learning/rag/01-retrieval.mjs --no-filter
node learning/rag/01-retrieval.mjs
node learning/rag/01-retrieval.mjs --grammar
```

依次观察：不筛体裁时通知卡相似度最高；筛体裁后邀请卡排第一；查询换成语法方向时通用规则排第一。前两次query向量相同，结果改变来自过滤，而不是模型突然“学会了”业务。

## 手算一次

查询q=(1,0)，邀请卡d=(0.9,0.1)：

```text
dot = 1×0.9 + 0×0.1 = 0.9
norm(q) = 1
norm(d) = sqrt(0.9² + 0.1²) = sqrt(0.82)
cos = 0.9 / sqrt(0.82) ≈ 0.9939
```

通知卡(0.99,0.01)的余弦约0.9999，反而更高。实际embedding也可能出现业务不适用的近邻；这个手工实验只展示这种可能性，不能拿这些数评价真实模型。

相似度不是考试分数，也不是答案正确概率。真正接模型时，向量每一维通常没有可直接命名的人类语义；本例两个轴是人为教学设定，不能说真实模型的第一个维度就是“邀请”。

## 三个动手任务

1. 把一个文档向量整体乘10，先预测余弦是否改变，再运行验证；对比直接点积。
2. 给邀请卡添加“正式公务邀请”的使用条件，分析仅用genre过滤为什么仍不够；这会引出元数据、相关性标注及reranker。
3. 把通用规则错误标成notice，再问语法问题，观察过滤如何造成漏召回；过滤需要正确数据，不是越严越好。

脚本内的断言只验证教学算式及构造场景。后续真实模型课程再讨论tokenizer、前缀、pooling、归一化及跨语言能力；紧接着先做结构化知识卡与关键词基线。

## 第一课应能复述

- embedding是表示，向量检索是寻找候选，生成模型负责组织回答，三者不是一回事。
- 元数据过滤限定允许的候选；相似度排序在允许集合内找近邻。
- 检索到文本还不等于RAG闭环，后面仍有证据组装、生成和引用验证。
- 零向量无法计算余弦，维数相同也不代表不同模型的向量可混用。
